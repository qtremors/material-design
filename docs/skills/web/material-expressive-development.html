Material 3 Expressive Web Development

Build and review responsive, accessible Material 3 Expressive components using independent vanilla HTML, CSS, and JavaScript implementations.

Use this skill for implementation work inside material-web/. Read the Material 3 Expressive development guide before adding a component and consult the component parity status for readiness.

Preconditions

  1. The matching Android entry must be marked Android Ready before web parity begins.
  2. Inspect the accepted Android UI/UX and document its states, interaction intent, and adaptive changes.
  3. Check current official Material guidance. Do not invent a browser API or assume Compose signatures apply to the web.

Implementation contract

  • Use semantic HTML, modern CSS, and vanilla JavaScript.
  • Keep tokens, components, state, tests, and releases independent from Android.
  • Express color, type, shape, spacing, elevation, and motion through web-owned custom properties.
  • Support keyboard, pointer, touch, assistive technology, forced colors where practical, and reduced motion.
  • Test compact, medium, and expanded layouts. Adapt to the available viewport rather than device labels.
  • Preserve user state and action outcomes when layout or input mode changes.

Component workflow

  1. Write a state table covering rest, hover, focus, pressed, disabled, selected, loading, success, and error states that apply.
  2. Choose semantic HTML and the accessible name, role, value, and keyboard model.
  3. Implement layout and tokens before decorative motion.
  4. Add expressive shape, typography, and motion without hiding state changes or delaying core actions.
  5. Verify responsive behaviour, zoom, long text, reduced motion, and keyboard-only use.
  6. Update the root TASKS.md, root CHANGELOG.md, and public HTML documentation.

Pattern-specific requirements

  • Split Buttons: Keep the primary action and menu trigger as distinct focusable controls with a shared visual group.
  • Wavy Progress Indicators: Preserve determinate versus indeterminate meaning and expose progress semantics; reduce or remove waves when motion is reduced.
  • Dynamic Typography: Treat variable-font axes as progressive enhancement and test reflow at every supported axis extreme.
  • Expressive Morphing Buttons: Keep press morphing brief and reversible; hold confirmation must provide progress, cancellation, and a non-hold alternative when required for accessibility.
  • Segmented Sections: Use the correct single- versus multi-select semantic model and retain readable focus boundaries across joined shapes.
  • Floating Navigation and Toolbars: Avoid obscuring content, account for safe areas, and keep every action keyboard reachable.

Completion checklist

  • UI/UX matches the accepted intent without sharing implementation code.
  • Compact, medium, and expanded layouts are verified.
  • Keyboard and screen-reader semantics are verified.
  • Reduced motion and 200% zoom remain usable.
  • Intentional platform differences are documented.
  • Parity and changelog entries are current.
