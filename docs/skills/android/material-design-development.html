Material Design Android Development

Develop and review the Material Design Android app references, including architecture, demos, terminology, theming, and porting constraints.

Use this skill for work inside material-app/.

Project Context

The installed Material Design app is a living, searchable Material 3 component gallery. The app is the visual truth and its modular repository source is the code truth. A person should be able to search an official component name, experience it, and give that same name or source path to an agent for reuse.

This is not a course, package store, documentation wrapper, or full-source browser. There are no simulated installs, ratings, accounts, placeholder catalog cards, or lesson progress.

Architecture

  • app/ is the composition root: activity bootstrap, typed navigation, adaptive application shell, ViewModel, and manual dependency container.
  • core/catalog/ owns the versioned JSON catalog, schema, typed models, validation, and deterministic alias/API search.
  • core/data/ owns local bookmarks, the 20 most recent component IDs, appearance settings, and reduced-motion preference through Preferences DataStore.
  • core/designsystem/ owns the app theme, inherited expressive motion specifications, reduced-motion behavior, and cross-cutting Material presentation.
  • feature/ owns Explore, Catalog/Search, APIs, Foundations, Detail, and Settings surfaces.
  • samples/ owns copyable state-hoisted implementations grouped by official domains: Actions, Communication, Containment, Navigation, and Foundations. Add a new domain module only when its first working reference exists.

Component Entry Contract

  1. Use the official Material component or foundation name. Put older project terms and common abbreviations only in searchable aliases.
  2. Keep the reusable composable independent of navigation, persistence, and feature ViewModels. Hoist state and callbacks.
  3. Build a real interactive reference with relevant variants, states, semantics, adaptive behavior, and increased-font support.
  4. Add exact API artifact/version metadata. Model stable-artifact versus alpha-only availability separately from stable versus experimental API status.
  5. Register the demo key and repository-relative source path in the bundled catalog. Every visible entry must map to real source and exactly one working demo.
  6. Add search, source validation, UI, accessibility, and adaptive light/dark coverage before exposing it.

Current Official Names

  • Buttons — aliases include expressive buttons and morphing buttons.
  • Button groups and Toggle buttons — grouped peer actions and persistent selected actions.
  • Split buttons — SplitButtonLayout.
  • Floating action buttons — aliases include FAB and extended FAB.
  • Progress indicators — aliases include wavy progress indicators.
  • Segmented list items — aliases include grouped lists and segmented sections.
  • Carousels — multi-browse and uncontained variants.
  • Cards and Lists — hierarchy, selection, interaction, responsive composition, and grouped rows.
  • Chips, Segmented buttons, and Selection controls — compact actions, filters, visible choices, and settings state.
  • Floating toolbars — horizontal and future vertical variants.
  • Typography — dynamic and variable typography remain searchable aliases.

Product-Surface Rules

  • Dogfood Material components where their real interaction purpose fits Explore, search, navigation, filters, settings, and details.
  • Do not recreate store fiction. “Featured” is curated, “Recently added” comes from catalog metadata, and “Recently viewed” is local history; never invent popularity metrics.
  • Keep search global and deterministic. Exact official names and API symbols outrank aliases, categories, and summaries.
  • Use adaptive navigation and layouts across compact, medium, and expanded windows. Carousels do not auto-play.
  • Retained custom behavior must be labeled Project implementation; never present it as an official API.

Motion Contract

Use core/designsystem/ExpressiveMotion.kt as the source for every explicit project spring value. It preserves the standalone app's distinct medium-bouncy press response, low-bouncy navigation and fluid layout response, no-bounce shape settling, high-stiffness progress smoothing, and rejected-action shake. Do not replace these with anonymous springs in feature code, and do not force every transition onto one shared spec: the compact navigation intentionally retains Material's default size, fade, expansion, collapse, and exit behavior around its custom low-bouncy lift and slide.

  • Pressed content scales to 0.94; compact navigation lifts the selected icon by 12.dp.
  • Hold confirmation keeps its 1.5-second safety interval and loading keeps its 1.2-second example interval.
  • Reduced motion snaps decorative movement and fades but preserves state changes, callbacks, haptics, and safety timing.
  • Cancel or retarget work safely on release, rapid repeat input, disabled-state changes, recomposition, and disposal. Never leave progress or transformed content stranded.
  • Keep official carousel, toolbar, progress-indicator, and navigation physics. Project springs supplement their state feedback; they do not impersonate a different official API.
