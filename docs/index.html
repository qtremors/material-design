Architecture and runtime

Boundaries that make every reference traceable.

A small application composition root connects typed routes, immutable state, a validated offline catalog, local preferences, feature screens, and domain-owned sample modules.

  1. 1

    Start and compose

    MainActivity creates the app container, catalog loader, user-library repository, and GalleryViewModel.

  2. 2

    Load and validate

    The bundled JSON catalog is parsed off the main thread and validated before entries are published.

  3. 3

    Publish independent state

    Catalog loading, search, category, destination, API stability, library, appearance, and one-shot events use focused flows.

  4. 4

    Adapt the shell

    Compact floating navigation or expanded navigation is selected from current window space, with state preserved across resizing.

  5. 5

    Resolve a stable identity

    Typed detail routes carry a catalog ID, then connect its metadata and source locations to exactly one registered demo.

  6. 6

    Persist locally

    Preferences DataStore stores bookmarks, recent IDs, theme state, accent selection, and reduced-motion choice.

Frequently asked questions

What this project is and how it behaves.

Is the Android app offline?

Yes. The manifest does not declare android.permission.INTERNET. The catalog is bundled in the APK and the app includes no ads, analytics, or tracking SDKs.

What information stays on the device?

Bookmarks, recent component IDs, theme mode, theme preset, accent choice, custom color values, and reduced-motion preference are stored in Preferences DataStore and excluded from cloud backup and device transfer.

Are all catalog entries working?

Yes. Every visible entry has a stable ID, exact official name, guidance, reviewed API metadata, real source paths, and exactly one registered demonstration. Incomplete ideas stay in the task backlog.

Are project experiments official Material APIs?

No. The catalog explicitly separates official APIs from project implementations, and separately models artifact availability and individual API stability.

Does Android share code with the web implementations?

No. The surfaces share design intent, terminology, states, accessibility goals, and adaptive behavior. Each platform owns its code, tokens, APIs, state, tests, and release lifecycle.

How can I contribute or report a problem?

Review the developer guide and active tasks, then use GitHub Issues for bugs, missing references, documentation gaps, and accessibility feedback.
